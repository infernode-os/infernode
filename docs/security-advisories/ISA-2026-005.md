Title: The TLS client did not authenticate servers

## Summary

Programs that use `tls` or `webclient` (the web browser's engine, the
agents' fetch tools, the LLM client, mail) did not authenticate the
server. Any one of these allowed a network attacker to impersonate any
HTTPS server:

- an X.509 chain did not have to reach a trust anchor: a self-signed
  certificate verified against itself, and an unknown issuer was taken;
- TLS 1.3 did not require Certificate and CertificateVerify;
- TLS 1.2 skipped the ServerKeyExchange signature when it was absent or
  not RSA;
- the host name check passed when an extension did not parse;
- PKCS #1 v1.5 signatures were verified by matching a suffix.

## Impact

Anyone on the network path could read and change every HTTPS
connection InferNode made, including API keys sent to LLM providers and
mail credentials.

## Fix

RFC 5280 path building to a root in `/lib/certs` with basicConstraints,
keyUsage and path length enforced; strict EMSA-PKCS1-v1_5, RSA-PSS and
ECDSA signature checks; Certificate and CertificateVerify required in
TLS 1.3 and the signed ServerKeyExchange in TLS 1.2; the host name
checked against subjectAltName only, failing closed. A connection that
cannot be authenticated is refused.

## Workarounds

None. Update to 0.5.0 or later, and rotate any credential an earlier
release sent over TLS on a network you do not control.

Found internally.
