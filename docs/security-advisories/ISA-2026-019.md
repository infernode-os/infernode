## Summary

login(6) is the encrypted key exchange `getauthinfo` uses to obtain a
certificate from a signer (`auth/logind`). Version 1 had lost what that
protocol is for:

- neither end checked the other's Diffie-Hellman value, so a client
  that sent 1 (or 0, p-1, p+1) made the shared secret a known number
  and was issued a certificate for **any account, with no password**,
  in CNSA mode or not;
- the signer sent its value sealed with an authenticated cipher under a
  key from the password, tag included, to anyone who named an account:
  one reply let passwords be tried offline, at leisure;
- the same client nonce sent again made the signer reuse a key and
  nonce;
- the client took the group (alpha, p) from whoever answered, with no
  floor, so an on-path attacker sending p = 2 was saved as the user's
  signer;
- names were used as they came, as keyfs directories and throttle keys
  (`carol/.` was carol to one and a different name to the other).

## Impact

Anyone who could reach a signer's login service could obtain a
certificate for any user of the realm and so authenticate as them to
every node that trusts the signer, or recover users' passwords from
recorded replies. An on-path attacker could install itself as a
client's signer.

## Fix

Version 2 of the exchange: fixed RFC 3526 groups (2048 bits at least,
3072 in CNSA mode); the signer's value masked with no tag under a key
from the password and both nonces; the client proves knowledge of the
secret before the signer sends anything derived from it; values outside
2..p-2 refused; names held to one account name. 0.12.0 made the
exchange version 3, adding ML-KEM.

## Workarounds

None. Update signers and every client to 0.11.0 or later. A realm that
ran `auth/logind` on a reachable network before 0.11.0 should make a new
signer key, enrol its users again and have them change their passwords.

Found by the project's security review.
