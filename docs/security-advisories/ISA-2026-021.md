## Summary

At 2048 bits, the size `createsignerkey -a elgamal` asks for, ElGamal
keys used RFC 3526's group 14 with generator 2, and verification asked
of r only that it lie between 1 and p-1. Because 2 divides p-1, the
choice r = (p-1)/2 with an s computed from the message verifies for any
message under any such key (Bleichenbacher, Eurocrypt 1996). Every
user's key takes the signer's group.

## Impact

Anyone with a signer's public key could make a certificate for any
name, and `Keyring->auth` accepted its bearer as that name: the review
forged one taken as "admin". Every node that trusted an ElGamal signer
could be entered as any user.

## Fix

Verification refuses an r outside the subgroup the generator spans and
an s outside 1..p-2, and keys whose generator or public value is not of
the subgroup's order. Key generation takes a random square as the
generator. Every ElGamal key made before is refused.

## Workarounds

None. Update to 0.11.0 or later, make the signer's key again (ML-DSA,
or ElGamal from the new code) and enrol its users again.

Found by the project's security review.
