## Summary

After `Keyring->auth`, auth(2)'s client names the ssl(3) algorithm the
connection is to use, in one clear-text message nothing vouched for.
Where a server would take `none` beside a cipher (`listen` or
`styxlisten` with `-M`), whoever carried the bytes could replace the
client's `aes_256_gcm` with `none`.

## Impact

The server ran the session it had just authenticated in clear and took
what the attacker wrote next as the client's requests, with the
client's identity. Servers started without `-M` were not affected.

## Fix

Version 2 of the exchange: the choice is sent with an HMAC under a key
from the shared secret, the server answers with its own, and ssl's
keys are derived from the client's words and the server's list, so a
change on the way fails at both ends. Both ends need 0.11.0 or later;
0.12.0 removed `-M`.

## Workarounds

Do not run `listen -M` or `styxlisten -M` on a release before 0.11.0.

Found by the project's security review.
