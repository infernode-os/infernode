## Summary

signer(8) signs a public key from anyone who connects and keeps the pad
that blinds the certificate in `/keydb/signed/<owner>` until an
operator approves it into `/keydb/countersigned`, where countersigner
gives it out. Both used names as they came:

- a key owned by `../signerkey` overwrote the signer's own key;
  `../../x` made a file anywhere the signer's user could write;
- a box id of `../signed/alice` had countersigner send the pad of a
  request nobody had approved.

`svc/auth` started both by default.

## Impact

With one connection, anyone who could reach the signer could destroy
the realm's signing key, or obtain a certificate from the realm's
signer for any name, with no operator and no password.

## Fix

Both take only one account name before touching a file; countersigner's
name space holds only approved records; the signer does not certify its
own name; `svc/auth` no longer starts signer or countersigner.

## Workarounds

Do not run signer or countersigner on a release before 0.11.0; stop
`svc/auth`'s copies on a reachable network. After updating, check that
the signer's key is the one you made.

Found by the project's security review.
