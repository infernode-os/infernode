## Summary

Limbo is type-safe, and InferNode relies on that to keep Limbo programs
inside their name
space. Programs compiled by the stock compiler could get outside it:

- storing runes into an empty, non-nil string ran over the blocks after
  it with values the program chose;
- an `alt` naming one channel twice freed the channel's queue, after
  which a value sent was stored where the Prog was receiving, a `big`
  where a pointer belongs;
- `chan[16r20000000] of big` wrapped its size to nothing and each send
  stored eight chosen bytes further up the heap; `IPint` shifts near the
  largest int wrote far past their block;
- the compiler kept addresses into heap objects across code that could
  free them (`g.n = <-c`, `c <-= g.n`, `a[i][f()]` and 18 other forms):
  a value arrived in, or was read from, whatever had been allocated
  there since.

## Impact

A Limbo program run on the system, by a user or by an agent whose
tools compile and run code, could write chosen values
into other objects in the shared heap and so escape the language's
safety, and with it the program's confinement.

## Fix

Each case is checked or rewritten: string room is counted in bytes, a
Prog is queued once on a channel, channel buffers and shift counts are
bounded before use, and both compilers keep only frame and module-data
addresses across anything that can free memory (with a screen,
`tools/limbo-stale-screen.py`, that finds none in the tree). Rebuild
your own modules with the 0.11.0 compiler.

## Workarounds

None. Update to 0.11.0 or later and recompile modules built with an
earlier compiler.

Found by the project's security review.
